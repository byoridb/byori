# Byori 프로젝트 안내서 — 개발 계획

**2026-09-12: 완료가 아닌 일시 중단.** 제품 방향을 원점에서 다시 검토하기로 했습니다.
현재 승인된 작업은 [프로젝트 의존 지식 재사용 실험](../dependency-context-pilot.md)입니다.
아래 내용과 기존 구현은 이력으로 보존하며, 새 가설을 검증하기 전에 앱 중심 계획을
계속 완성해야 한다는 전제로 사용하지 않습니다.

방향 확정: **2026-09-11**. 제품 결정과 구현 의존성의 최종 책임자는 저장소 유지관리자입니다.
코딩 에이전트와 함께 개발하되, 저장소가 둘이라고 개발팀도 둘인 것으로 계산하지 않습니다.

상태: **2026-09-11 구현 승인 후 KC-01 진행 중. 이후 단계의 완료 조건은 아직 통과하지 않았습니다.**
소유자가 적절한 에이전트·모델 배분을 통한 구현과 독립 검증을 추가로 요청했습니다.
이미 존재하는 기능은 재사용 자산이지 새 단계의 완료 실적이 아닙니다. 별도 요청 없는 배포·데이터 삭제·
백그라운드 작업 등록·전면 재작성은 범위에 포함하지 않습니다. 아래 실행 체크포인트를 참고하세요.

## 1. 만들 제품과 범위

**Byori는 AI가 읽는 프로젝트 안내서를 만들고 최신으로 유지합니다.**

사용자에게 약속할 문장: **“프로젝트 설명, 매번 다시 하지 마세요.”**

```text
신뢰한 프로젝트 + 선택한 원본 + 확정된 체크포인트
    → 근거가 연결된 기록과 의존성 그래프
    → 짧은 버전별 안내서 + 필요할 때 조회하는 상세 근거
    → 사용자가 이미 쓰는 Claude Code / Codex
    → 원본 변경 → 영향받은 기록 재생성 → 안내서 갱신
```

Byori가 사용자에게 보이는 하나의 제품이고, ByoriDB는 내부 지식 빌드 엔진입니다.
원본과 확정 기록은 보존하며 그래프 투영과 안내서는 다시 만들 수 있는 결과물로 둡니다.
앱은 프로젝트 연결·안내서 미리보기·에이전트 연결·갱신 문제 확인을 위한 작은 매니저가 됩니다.
[PRODUCT.md](../../PRODUCT.md)가 제품 범위, [DESIGN.md](../../DESIGN.md)가 목표 매니저와
전환 중 유지할 기존 UI의 기준입니다.

### 첫 출시의 경계

| 반드시 포함 | 근거가 생길 때까지 보류 |
|---|---|
| 프로젝트 선택, 제한된 원본 수집, 근거 있는 미리보기 | GitHub 이슈·PR 본문 전체 수집, 추가 커넥터 |
| 짧은 안내서, 출처, 미해결·오래됨 표시 | 대화 전체에서 자유롭게 지식을 추출하는 기능 |
| Claude Code·Codex 새 세션에 실제 전달 | 추가 에이전트, 범용 멀티 에이전트 실행 관리 |
| 변경 기반 갱신, 수동 갱신, 오프라인에서 읽을 수 있는 결과 | 쉬지 않는 모델 요약, 자동 정책 확정 |
| 되돌릴 수 있는 설치·연결, 복구 가능한 이전 | DB 전면 재작성, 즉시 저장소 합병, 기존 데이터 삭제 |

모델을 이용한 편집은 결정론적 흐름을 확인한 다음의 선택 기능입니다. 첫 효용 검증을 막지 않습니다.
실사용자가 현재 소유자 한 명인 상황에서 도달 사용자 수나 시장 규모를 꾸며 우선순위를 계산하지 않습니다.

## 2. 개발 순서

날짜를 미리 약속하지 않습니다. 한 번에 한 단계를 진행하고, 대략 개발일 다섯 중 하루는 테스트·통합·
결함 대응에 남깁니다. KC-01과 각 단계 완료 후 작업량을 다시 추정합니다. 일이 커지면 커넥터·AI 편집·
시각적 꾸미기를 줄이며, 데이터 보존이나 출처 검증을 줄이지 않습니다. 다음 출시 경계로 넘어가기 전에
소유자가 완료 조건을 확인합니다.

### KC-01 — 프로젝트 하나에서 쓸 만한 안내서 만들기

검토 가능한 변경 세 개로 나눕니다.

1. **계약과 테스트 자료.** 프로젝트·체크아웃 식별자, 수집 범위, 확정 기록 필드, 빌드 버전,
   주장 상태, 생성물 소유권과 공개 경계를 정합니다. 결정·대체 결정·이유 없는 revert·주의사항·
   문서 변경을 가진 작은 테스트 저장소를 만듭니다. 튜닝 전에 비교할 질문을 고정합니다.
2. **원본 어댑터.** `cli/archaeology.py`의 Git·문서 추출을 재사용하고 기존 기억은 얇은 저장소
   어댑터로 읽습니다. 원본 위치와 확정된 체크포인트 본문을 보존합니다. 모든 revert를 해결된 버그로,
   모든 ADR을 현재 유효한 결정으로 간주하지 않습니다.
3. **결정론적 컴파일러.** `cli/` 아래 공유 모듈로 정규화 → 선별 → 렌더링 → 검증 → 공개를
   구현합니다. 추출과 렌더링은 독립 테스트가 가능해야 합니다. 기존 `byori init`의 옵션·JSON 계약을
   깨지 않고 확장합니다. 새 갱신 명령이나 출력은 명시적으로 버전 관리합니다. 미리보기·dry-run은
   에이전트 설정을 바꾸지 않습니다. 생성 위치 후보는 `.byori/handbook.md`이며 공개 인터페이스로
   쓰기 전에 소유권과 Git 제외 방식을 확정합니다.

안내서 v1: 목적, 핵심 모듈, 근거 있는 결정·제약, 주의사항, 아직 모르는 것. 중요한 주장마다 기록 ID와
원본 위치를 붙입니다. 근거가 없으면 표시하고 만들어 넣지 않습니다. 현재 자료를 이용한 작은 미리보기를
우선하며, 오래된 전체 히스토리 보강은 명시적으로 선택하고 중단·재개할 수 있게 합니다. 제외·잘림을 표시합니다.

완료 조건: 같은 스냅샷·컴파일러 버전이면 바이트 단위로 같은 결과. 테스트 자료의 주장은 근거가 있거나
한계가 표시됨. 문서 속 명령을 실행하지 않음. 누락된 원본·비밀정보·충돌·작은 문맥 예산 테스트 통과.
모델 계정이 없어도 작동합니다. 모든 저장소에 충분한 근거가 있다고 약속하지 않습니다.

### KC-02 — 에이전트가 실제 읽는 것까지 연결하기

1. 테스트 대상 Claude Code·Codex 버전의 시작 시점·지침 로딩 수단을 확인하고 호환성 테스트로
   호스트별 전달 경로 하나를 정합니다. MCP 등록만으로 자동 주입이 된다고 가정하지 않습니다.
   두 도구가 같은 파일이나 훅을 지원한다고도 가정하지 않습니다. 자동 전달이 불가능하면 제한을
   노출하고 해당 완료 조건을 실패로 남깁니다. 수동 단계를 자동이라고 부르지 않습니다.
2. 연결 변경 미리보기, 관리 구역의 제한적 참조 삽입, 백업, 정확한 연결 해제를 구현합니다.
   사용자 `CLAUDE.md`·`AGENTS.md`·설정·기존 지침을 통째로 덮어쓰지 않습니다. 관리 구역의
   충돌이나 수동 편집은 감지해 검토를 요청합니다.
3. 시작할 때 짧은 안내서와 생성 버전·범위를 전달하고, 상세 근거는 기존 MCP 조회로 제공합니다.
   필요할 때만 생성 버전을 지정하는 작은 읽기 전용 진입점을 추가합니다. 또 다른 메모리 API를
   만들지 않습니다. 생성 텍스트는 참고 문맥이며 사용자 정책을 덮어쓸 수 없습니다.
4. 배포용 Memory Skill과 MCP 지침을 함께 바꿉니다. 원본·확정 기록이 기준이고 컴파일러가
   소유한 읽기 전용 안내서는 허용된 파생 뷰입니다. 별도로 사람이 관리하는 호스트 메모리 사본은
   만들지 않습니다. 구조화된 체크포인트 기록은 유지합니다.

완료 조건: 각 에이전트의 새 프로세스가 매번 수동 recall 요청 없이 지정된 생성 버전을 받음.
통제된 테스트에서 프로젝트 제약을 설명하고 출처를 열 수 있음. 원본 변경 → 명시적 재빌드 → 새 세션에서
대체 내용 확인. 연결·해제 후 기존 사용자 내용 보존. 테스트 프로필과 승인된 모델 접근만 사용하며 실제
개발자 에이전트 설정을 테스트가 몰래 수정하지 않습니다.

### KC-03 — 바뀐 것만 안전하게 갱신하기

1. 앱·CLI·MCP가 같은 조정기를 사용합니다. 선택 원본과 확정 기록 버전을 해시로 확인하고 변경을
   모아서 중복 작업을 제거한 뒤 영향받는 의존성만 재빌드합니다. 수동 갱신과 세션 시작 시 최신성
   확인부터 구현합니다. 백그라운드 갱신은 명시적 동의와 조절 가능한 한도로 활성화합니다.
   끊임없이 모델을 호출하는 반복 작업은 만들지 않습니다.
2. 프로젝트, 체크아웃 식별자, Git·미커밋 상태 해시, 원본 정책, 기록 버전, 스키마·컴파일러 버전으로
   빌드를 구분합니다. 모델을 쓰면 모델·프롬프트 버전도 포함합니다. 체크아웃별 중복 빌드를 막고
   프로젝트 공통 확정 기록 쓰기도 조정합니다.
3. 변경 불가능한 생성 버전을 준비·검증한 뒤 한 공개 경계에서 활성화합니다. 안내서와 상세 근거는
   같은 생성 버전을 가리켜야 합니다. 공개 직전 입력 스냅샷을 재확인해 오래된 작업이 새 결과를
   덮지 못하게 합니다. 파일을 여러 번 따로 rename하는 것만으로 원자적 공개라고 부르지 않습니다.
4. 변경 감지·빌드 중·최신·실패·제외/철회 상태를 엔진 상태 및 전달 상태와 구분합니다. 일반 오류는
   마지막 정상 결과를 스냅샷·오래됨 경고와 함께 읽을 수 있게 합니다. 다른 체크아웃의 결과나
   철회·비밀정보 결과는 제공하지 않습니다. 오프라인이라고 안전하지 않은 대체 결과를 허용하지 않습니다.

완료 조건: 변경 없으면 모델 호출 없음. 중단돼도 완전한 이전 또는 새 생성 버전 유지. 연결된 워크트리끼리
실험적 지식이 섞이지 않음. 브랜치 전환·미커밋 편집은 이전 뷰를 무효화함. 재시도·취소·롤백 반복 안전성.
허용된 공개 안내서는 엔진 로그인 없이 읽을 수 있음. 의존성 추적이 불완전한 일부 빌드를 최신으로 표시하지 않음.

### KC-04 — 작은 매니저와 믿을 수 있는 설치로 묶기

1. 기존 프로젝트 등록·빈 Context 진입점을 **프로젝트 연결 → 안내서 미리보기 → 에이전트 연결**로
   바꿉니다. 중심은 그래프 그림이 아니라 읽을 수 있는 안내서입니다. 출처·미해결 항목·마지막 성공
   스냅샷·빌드 상태·재시도를 보여줍니다. ‘설정됨’과 ‘마지막 전달 검증’을 구분합니다. 키보드·VoiceOver·
   밝은/어두운 화면·빈 프로젝트·대형 프로젝트·오프라인·실패 상태를 확인합니다.
2. SwiftUI·`ManagerService`를 재사용하고 CLI·MCP와 같은 컴파일러·조정기를 호출합니다.
   `byori init`과 프로젝트 ID 호환성을 보존합니다. 첫 미리보기에 터미널 세션·워크트리·포트·그래프
   공간명·DB 비밀번호를 알 필요가 없어야 합니다.
3. 앱·설치 스크립트 뒤 런타임 생명주기 관리 주체를 하나로 만듭니다. 검증된 앱·CLI·MCP·스키마·
   엔진 조합을 고정하고 서명 검증, 업데이트·재시작 직렬화, 버전·manifest를 포함한 롤백을 보장합니다.
   doctor는 원본 접근·빌드·안내서 최신성·연결 상태까지 확인합니다. 설치 오류를 숨기지 않습니다.
4. 아래 이전 절차를 통과한 후 기존 워크스페이스 진입점을 주 화면에서 내립니다. 코드 삭제는 별도
   범위의 변경이며 데모의 선행 조건이 아닙니다.

완료 조건: 새 테스트 계정에서 설치·프로젝트 선택·유용한 내용 확인·각 지원 에이전트 연결·실패 복구를
완료할 수 있음. macOS 두 아키텍처와 기존 서명 체계 확인. Linux CLI 호환성은 유지하되 새 Linux GUI는
만들지 않음. 설치 테스트는 격리된 홈·포트·데이터만 사용하고 실행 중인 개발자 엔진을 건드리지 않음.

### KC-05 — 선택적 AI 편집기, 사실을 만들어 내는 장치는 아님

공급자 교체가 가능한 인터페이스에 첫 실험용 공급자 하나를 명시적으로 선택합니다. 자격증명·권한,
외부 전송 내용 미리보기, 비용 계산과 한도, 타임아웃·취소를 먼저 정합니다. Claude/Codex 구독을
자동으로 재사용할 수 있다고 가정하지 않습니다.

모델은 제한된 원본 근거·확정 기록을 읽고 출처 ID·조건·충돌이 있는 구조화된 주장을 제안합니다.
의미·범위·근거가 일치할 때만 중복 표현을 합칩니다. 이전 요약만으로 새 사실을 만들지 않습니다.
스키마·실제 근거·범위·금지 내용을 검증합니다. 형식 검증이 의미 검증은 아니므로 불확실한 제안은
검토 대상으로 남깁니다. 새 행동 규칙의 확정은 명시적 수락이 필요합니다.

완료 조건: 튜닝에 쓰지 않은 과제에서 KC-03 대비 개선되고 중대한 사실 오류가 늘지 않음.
빌드·프로젝트별 비용 상한 강제. 거절된 결과가 마지막 안전한 빌드를 훼손하지 않음.
변경 없으면 모델 요청 없음. 개선을 보이지 못하면 이 단계는 출시하지 않습니다.

### KC-06 — 제품 가설 검증과 출시 판단

Byori·ByoriDB를 별도 프로젝트로 직접 사용한 다음, 동의한 외부 개발자 다섯 명을 제한된 파일럿에
초대합니다. 자동 원격 측정은 하지 않습니다. 각자 새 세션 세 번과 원본 변경 한 주기 이상 사용하도록
요청합니다. 잘 된 데모뿐 아니라 실패·반복 수정도 기록합니다. 다섯 명은 방향을 배우기 위한 규모이며
통계적 증명이 아닙니다.

아래 비교 평가를 수행하고 한계도 공개합니다. 안전성과 반복 사용 가치를 확인한 후 매니저·CLI·MCP를
하나의 호환 묶음으로 출시합니다. 기존 코드 정리는 보존·복구 검증 이후입니다. 사람이 관리하는 Markdown보다
관리 노력이나 최신성이 나아지지 않으면 팀·클라우드 기능보다 핵심 흐름 개선 또는 범위 축소가 먼저입니다.

## 3. 공통 기술 계약

### 원본과 기록

- 선택한 tracked 문서, 범위가 정해진 Git 히스토리·메타데이터, 기존 확정 기억, 명시적 체크포인트가
  입력입니다. Git의 PR 번호는 참조이지 원격 본문을 읽었다는 증거가 아닙니다. 네트워크 수집은
  별도 동의와 후속 어댑터가 필요합니다.
- 심볼릭 링크·정규 경로를 확인하고 선택한 루트 경계를 강제합니다. 비밀정보·`.env`·비공개 ignored
  경로·생성 결과·대화 원문은 기본 제외합니다. 문서 속 명령 실행이나 진단 중 자격증명 출력은 금지합니다.
- 기록 필드: 안정적인 ID, 종류, 본문, 원본 위치·내용 해시, 프로젝트/체크아웃 범위, 원본 사건 시각,
  기록 시각, 마지막 검증 스냅샷, 주장 상태, 관계. 상태는 `supported`, `inferred`, `conflicted`,
  `superseded`, `unverified`의 의미를 문서화합니다. ‘근거 있음’은 SHA 문자열 발견 이상의 주장별 판단입니다.
- 원본 사건 시각과 DB 기록 시각은 다릅니다. 옛 커밋을 오늘 넣었다고 당시 DB 스냅샷이 생기지 않습니다.
  엔진의 전체 이중 시간 질의 확장은 MVP 선행 조건이 아니지만 앱 메타데이터는 구분을 보존합니다.
- 그래프를 재생성 가능한 투영으로 취급하기 전에 그래프에만 있는 확정 기록을 복구 가능한 기준
  기록 저장소로 보존합니다. 원본 제외는 관련 파생 결과를 무효화합니다. 실제 삭제는 단순 숨김이 아니라
  보존·백업 정책까지 정해야 합니다.

### 결과물과 저장

현재 ByoriDB 계약 위에 얇은 어댑터를 둡니다. 원본 어댑터·기록 정규화/저장·컴파일러/검증기·생성 버전
저장·조정기·호스트 어댑터로 내부 모듈을 나눕니다. 새 서비스 여섯 개를 만들자는 뜻이 아닙니다.
생성 버전 공개는 조정기만 담당하고, 기존 메모리 도구는 확정 체크포인트를 쓰고 무효화를 알릴 수 있습니다.

짧은 문맥 예산, 안정적 순서, 주장별 참조, 생성 버전 ID를 두고 상세 내용은 필요할 때 읽습니다.
생략된 부분과 낮은 자료 충실도를 표시합니다. 생성 파일 수동 편집은 원본 수정 후보로 안내하며,
몰래 다시 입력으로 수집하거나 아무 일 없던 것처럼 덮어쓰지 않습니다.

KC-02 호스트 연결이 의존하기 전에 KC-01에서 파일 배치와 단일 생성 버전의 공개 경계를 확정합니다.
KC-03은 그 인터페이스를 깨지 않고 동시성·무효화 처리를 강화합니다. 스키마 변경 중에도 원본은
복구 가능해야 합니다. 언어 전면 교체·분산 그래프·새 쿼리 언어·두 번째 DB는 전제하지 않습니다.

엔진 작업이 필요하면 upstream 이슈와 계약 테스트를 먼저 만들고 호환 릴리즈를 조정합니다.
막혔다고 운영 저장 엔진을 몰래 바꾸지 않습니다.

## 5. 데이터 이전·롤백·통폐합

1. **목록 확인:** 정확한 프로젝트 ID·경로·공간, 엔진·스키마 버전, 설정, 사용자 지침 파일,
   기존 작업·세션 메타데이터를 확인합니다. 비밀정보는 노출하지 않습니다.
2. **백업 후 복사본 복구:** 그래프, 그래프에만 있는 확정 기록, 레지스트리, 원본 정책,
   런타임·설정 manifest, 연결 전 설정을 포함합니다. 저장소 관리 주체와 일관된 백업을 만듭니다.
   현재의 개수 제한 `memory_export`는 진단용이지 전체 백업이 아닙니다.
3. **역사를 바꾸지 않고 가져오기:** ID·원본 위치·본문 보존. 근거가 부족한 옛 주장은 `unverified`로
   두며 확정된 현재 정책으로 재해석하지 않습니다.
4. **병행 미리보기:** 격리한 복사본에서 새 투영을 생성하고 ID·개수·선별한 지식을 비교합니다.
   소유자가 안내서를 검토하는 동안 기존 동작 환경은 유지합니다.
5. **되돌릴 수 있는 전환:** 검증된 생성 버전과 명시적으로 승인한 호스트 수정만 활성화합니다.
   롤백은 런타임 메타데이터·설정·이전 안전한 결과를 복원하고, 새로 기록된 원본은 재처리를 위해 보존합니다.
6. **별도 정리:** 새 흐름이 동작한 후 기존 UI를 뒤로 내립니다. 이름이 특정된 불필요한 코드·자산만
   이후 별도 검토 변경으로 삭제합니다. 기억·원본 저장소·브랜치/워크트리·자격증명·작업/세션 데이터는
   이번 방향 결정의 삭제 대상이 아닙니다.

실행 중인 ByoriDB에서 파괴적 이전·서비스 테스트를 하지 않습니다. 홈·포트·데이터 복사본을 격리합니다.
오래된 안내서 한 장은 원본 백업을 대신하지 않습니다.

## 6. 검증과 출시 조건

### 자동 테스트

- 근거: 이유 없음, 끊어진 참조, 문서 이동, 상충 ADR, revert, 대체 관계, 근거 없는 모델 주장,
  체크포인트에만 남은 지식.
- 경계: 비밀정보, 심볼릭 링크 탈출, 프롬프트 주입, 생성물을 다시 먹는 루프, 같은 이름의 저장소,
  연결된 워크트리, 미커밋 변경, 대형·잘린 입력.
- 생명주기: 결정론·변경 없음, 의존성 무효화, 빌드 중 원본 변경, 동시 공개, 충돌 종료, 취소,
  엔진 오프라인, 철회, 롤백.
- 전달: 실제 새 프로세스, 생성 버전·범위, 기존 설정 보존, 관리 파일 수동 편집, 업그레이드·해제,
  지원되는 시작 경로가 없는 호스트.
- 호환성: 영향받은 Python·MCP·고정 엔진 smoke, Swift 테스트·self-test·엄격한 동시성 검사,
  패키징·서명 검증. 컴파일러 테스트는 격리된 자료를 기본 사용합니다.

### 공정한 비교

튜닝 전에 원본·질문을 고정합니다. 결정·대체·실제 변경이 있는 여러 저장소를 사용합니다.
에이전트·모델·자료 범위·도구 접근·과제 예산을 맞추고 순서를 무작위로 바꾸어 반복합니다.

1. 에이전트 + 현재 코드·문서·Git. Byori가 미리 만든 문맥 없음.
2. 같은 원본 + 사람이 관리하는 짧은 Markdown 안내서. 작성·갱신 노력도 비용으로 포함.
3. 같은 문맥 예산의 Byori. 수집·편집·갱신·추론 비용 모두 포함.

정확성, 실제 출처의 뒷받침, 조건 보존, 폐기된 규칙 사용, 과제 결과, 사용자 수정·준비 시간,
첫 사용 지연과 총비용을 봅니다. 역사 질문뿐 아니라 현재 코딩 과제를 포함합니다. 별도 평가 질문과
변경 후 스냅샷은 튜닝에 쓰지 않고 실패도 공개합니다. 그래프 순회를 단순 기록 인덱스로 대체하는
비교를 통해 내부 복잡성의 가치를 확인합니다. 기존 Redis 8/8 대 빈 그래프 0/8은 이 비교가 아닙니다.

### 임시 목표 — 측정된 실적이 아님

- 정해진 출시 안전 테스트에서 비밀 유출·체크아웃 간 문맥 유출·설정/데이터 손실·중대한 근거 없는
  규칙이 관측되지 않아야 합니다. 한 건이라도 발생하면 출시를 막습니다. 유한한 테스트 통과가 모든
  환경에서 안전하다는 증명은 아닙니다.
- 공개된 테스트 주장 모두의 출처를 찾을 수 있고 실제 뒷받침·조건 검토를 통과해야 합니다.

## 9. 동의 기반 갱신 체크포인트 — 2026-09-12

`sync`를 한 번 요청하지만 실제 호스트 전달은 계속 미검증입니다. 기존 읽기 전용 연결은 보존하며 명시적으로

저장한 원본 한도·제외 경로를 미리보기·수동 빌드·`init --handbook`·sync·MCP 읽기 모두 따릅니다.
명시한 옵션과 저장 정책이 충돌하면 범위를 넓히지 않고 거부합니다. 설정 변경은 검토한 버전으로 확인하며,

설정 파일은 저장 전에 직렬화된 크기를 확인합니다. 변경 없는 갱신은 새 결과를 공개하거나 모델을 호출하지 않습니다.

독립 검증에서 읽기 후 취소·끄고 켜기 사이의 버전 재사용·읽기 한도를 넘는 제외 설정 문제를 찾아 수정했습니다.
최종 독립 테스트 **38개가 132.338초에 통과**했고, 이후 추가한 ‘설정 없음’ CLI 검증도 통과했습니다.
통합 Python 기준 트리는 **419개 / 441.336초** 통과했습니다. 이후 추가한 CLI 두 사례를 포함한 최신 갱신

표현하지 않습니다. 테스트 자식 프로세스의 파이프를 명시적으로 닫은 뒤 MCP 생명주기 테스트는
`ResourceWarning` 오류 취급으로 **46개 / 2.284초** 통과했습니다. 최종 통합 Swift 테스트는
**326개 / 37.111초** 통과했고, 임시 저장소에서 실제 CLI 설정 응답을 읽는 테스트도 포함합니다.
arm64 엄격한 동시성·경고 오류 빌드(29.09초), 코어 self-test, 설치/DMG 스크립트 문법 검사와
`git diff --check`도 통과했습니다. 실제 화면·유니버설 바이너리·공증·설치 서비스·롤백 검증을 대신하지 않습니다.

원본 수집 테스트의 커밋 12개에서는 `git cat-file`을 메타데이터·본문 두 번만 실행했습니다. 결과의 형식·ID를

이는 갱신 구현 한 묶음의 완료이지 **KC-01~KC-04 또는 전체 목표 완료가 아닙니다.** 아직 선택 원본을

## 10. 조건을 보존하는 선별·진단 체크포인트 — 2026-09-12

명시된 충돌·대체 관계는 조건과 함께 전부 보여주거나 함께 보류합니다. 한쪽 본문이 비어도 다른 쪽만

있는 작은 원본에서도 생략 설명 때문에 근거 파일 한도를 넘지 않습니다. Markdown 코드 구분자의 종류와
길이를 확인해 예제 속 제목·상태를 원본의 정책 상태로 오독하지 않습니다. 유효한 유니코드는 원문대로
보존하되 제어 문자나 부적절한 경로는 거부합니다. 모델 호출이나 근거 없는 신뢰도 승격은 없습니다.

매번 선택 원본을 새로 읽고 검증합니다. 한도가 있는 **프로세스 내 메모**는 바뀌거나 삭제된 원본과 그에
의존하는 결과만 다시 계산하며, 타입 관계 변경은 이전·새 그래프를 함께 확인합니다. 최종 선별·렌더링·
공개 검증은 다시 합니다. 처음부터 계산한 결과와 재사용 결과는 바이트 단위로 같고, 호출자가 반환값을
바꿔도 내부 결과가 오염되지 않습니다. 범위·버전을 격리하며 실패한 계산은 이전 정상 메모를 대체하지
않습니다. 별도 CLI 실행은 처음부터 시작하므로 실행 간 영속 증분 컴파일 조건은 아직 미통과입니다.

`doctor PATH --handbook-only`는 엔진 인증·런타임 환경 파일·일반 호스트 프로필 조회나 파일 변경 없이
원본 접근·결과 최신성·생략·갱신 동의와 한도·프로젝트별 Claude/Codex 연결 무결성을 진단합니다. 자동 갱신
꺼짐은 의도한 상태, 결과 없음·오래됨은 경고, 검증 불가는 실패입니다. 연결됨을 실제 전달됨으로 표시하지
않습니다. 기존 기본 doctor 동작은 유지합니다. 배포 파일만 복사한 테스트에도 이 진입점과 새 모듈을 포함했습니다.

독립 검증은 **44개**(적대적 사례 24·메모 13·파서 7, 전체 28.779초) 통과했습니다. 의미 있는 원본·조건의
선별, 공개 경합, 새 프로세스의 재계산도 확인합니다. 원본 선언 테스트 32개, 새 진단 27개와 기존 doctor
27개도 작업자가 확인했습니다. 메인에서 배포 런타임 1개·MCP 연결 5개와 Swift **326개 / 11.730초**
(빌드 15.69초)를 다시 검증했습니다. 이 저장소의 읽기 전용 진단은 공개한 안내서 없음·의도된 갱신 꺼짐·
호스트 미연결/전달 미검증을 정확히 보고했으며 빌드·연결·복구를 실행하지 않았습니다.

실제 저장소를 커밋 20개·문서 20개로 제한한 관찰에서는 원본 36개·인용 22개·생략 234개를 11,589자로
반환했습니다. 최초·재사용·전체 재계산 결과가 완전히 같았고 원본별 재계산 개수는 각각 36·0·36이었습니다.
시간은 0.235·0.227·0.250초로, 올바른 재사용의 증거이지 큰 전체 성능 향상이나 지식 품질 비교의 증거는
아닙니다. arm64 엄격한 동시성·경고 오류 빌드(15.32초), 코어 self-test, `ResourceWarning` 오류 취급
MCP 생명주기 46개(1.368초), 셸 문법·diff 공백 검사도 통과했습니다.

모든 런타임·테스트 파일을 확정한 뒤 최종 통합 Python **524개 / 481.228초**가 실패·오류·건너뜀 없이
통과했습니다. 이전 중간 검사 489개만이 아니라 새 진단과 대량 생략 회귀까지 포함한 결과입니다.
실행 중인 테스트 프로세스는 남기지 않았습니다.

확정한 전략과 제품 범위는 그대로입니다. KC-01/KC-03/KC-04를 향한 진전이지 완료가 아닙니다. 실제 호스트
전달에는 별도로 인증한 비공개 테스트 프로필이 필요합니다. 그래프 원본 보존·안전한 마지막 정상 결과와
오프라인 복구·실행 간 증분 재사용·통합 런타임/설치/롤백·실제 화면·아키텍처/서명·비교 평가·파일럿은
남아 있습니다. 검증 중 디스크 여유가 약 5GB라 대형 DMG/유니버설 빌드는 시작하지 않았습니다. 인증정보
복사·서비스 실행·운영 프로필 변경·커밋 푸시·배포는 하지 않았습니다. ByoriDB 조회/체크포인트는 연결 거부로
불가했으며 구현 체크포인트는 저장소 문서에 남깁니다. 별도 호스트 메모리로 제품 결정을 대체하지 않습니다.
## 11. 런타임 소유권과 로컬 연결 진단 — 2026-09-12

앱 설치/시작/중지/재시작과 단독 설치기가 같은 비공개 OS 파일 잠금을 사용합니다. 취소와 별도
롤백 작업까지 소유권을 유지하고, FD 9의 명시적 전달로 번들 실행 및 `curl | bash`를 모두
지원합니다. 잘못된 경로/권한/디스크립터와 동시 실행은 변경 전에 거부합니다. 제거 시에도 잠금
파일과 루트를 보존하고, 백그라운드 엔진에는 잠금을 넘기지 않습니다. 엔진 manifest는 원자적으로
교체하며 앱의 런타임 설치는 사용자 MCP/스킬/훅을 자동 변경하지 않습니다.

런타임 스냅샷에는 engine.json 및 크기가 제한된 바이트/권한 목록이 포함됩니다. 복원 전 전체를
검증하고, 서비스/포트 중지를 확인한 뒤 데이터와 스냅샷을 다시 검사합니다. 엔진이 바뀌었고 데이터가
존재하면 호환성 검증 없이 이전 엔진을 덮어쓰지 않습니다. 원본 그래프 데이터는 삭제하지 않습니다.
이는 일관된 DB 백업이나 다중 파일의 충돌 안전 복원이 아닙니다. 이 완료 조건들은 여전히 열려 있습니다.
[런타임 계약](../runtime-mutation-contract.md)에 정확한 범위를 기록했습니다.

파일 고정 후 **설치기 50개 테스트 / 236.217초** 통과, strict-concurrency와 warnings-as-errors를
적용한 **Swift 전체 353개 / 15.949초** 통과(최종 리뷰 수정 반영), 수정한 자체 검증 PASS(최초 수정 빌드 8.91초),
셸 문법과 diff 공백 검사 통과입니다. 실제 OS 잠금과 FD 전달은 검증하되 서비스/엔진/네트워크는
격리된 가짜 실행 대상을 사용했습니다. 최초 설치기 검증의 호환성 기대값 두 건과 테스트 중 파일
수정으로 생긴 오류는 수정 후 전체를 다시 실행했으며, 최종 수치는 그 고정된 성공 실행만 가리킵니다.

사용자가 요청한 로컬 연결 진단에서는 MCP 주소 불일치가 아니라 엔진/포트/서비스가 없는 상태를
확인했습니다. 서버의 9월 11일 21:12:02(KST) 종료는 이 작업의 21:11:54 자체 검증 실행 직후였습니다.
기존 설치 취소 테스트가 임시 HOME만 바꾸고 실제 서비스 이름/명령 실행기를 사용하여, 복구 경로에서
사용자의 엔진을 내릴 수 있었습니다. 원인일 가능성이 높지만 신호 발신자를 직접 기록한 증거는 없습니다.
따라서 **앞선 자체 검증 실행에 관한 ‘실제 서비스에 영향 없음’ 주장은 정정/제한합니다.** 테스트는
고유 서비스 이름과 기본 차단 실행기로 수정했습니다. [진단 상세](../local-engine-diagnosis-2026-09-12.md).
이번 진단에서는 실제 엔진을 재시작하거나 설치/설정을 변경하지 않았습니다.

사용자 지시에 따라 이 작업의 Orca 조정은 제외하고 Codex 작업자를 직접 사용합니다. Orca는 Byori
런타임이나 ByoriDB MCP의 의존성이 아니며, 다른 프로젝트/Orca 프로세스/전역 스킬과 설정은 건드리지
않았습니다. 엔진 복구 전에는 그래프 기록 성공을 주장하지 않습니다. 커밋/푸시/배포/호스트 프로필
마이그레이션 또는 전체 제품 목표의 완료를 의미하지 않습니다.

## 12. 실행 간 중간 결과 재사용과 승인된 엔진 복구 — 2026-09-12

컴파일러 1.2.0은 한도가 있는 프로세스 내 메모에 체크아웃별 Git 메타데이터의 인증된 디스크 캐시를
연결합니다. 실행할 때마다 선택 원본과 명시적 선언은 다시 읽고 검증합니다. 원본 내용·상태·조건의
변경/삭제와 관계 변경은 이전/새 그래프 양쪽에서 역방향 의존 범위를 무효화합니다. 최종 선별·출력·
근거 식별자·공개 직전 재검증은 생략하지 않습니다. 성공한 일반 빌드만 캐시를 저장하며 미리보기,
읽기 전용 명령, 실패/취소, `--clean`은 저장하지 않습니다. clean은 공개 재검증까지 두 캐시를 모두
우회하여 독립적인 전체 재계산 비교 경로로 유지합니다.

비공개 32바이트 HMAC 키는 캐시의 범위와 내용을 검증할 뿐 원본 주장이 참이라고 보증하지 않습니다.
변조·범위 불일치·잘못된 권한/경로·잠금 경합은 전체 재계산 또는 저장 생략으로 처리합니다. 키를
호스트 인증 정보나 결과물에 넣지 않습니다. 같은 사용자 권한으로 키/컴파일러를 장악한 공격은 보장
범위 밖입니다. 이미 로드한 코드의 지문을 사용하므로 디스크 코드가 교체돼도 예전 프로세스가 새
구현의 결과인 것처럼 저장하지 않습니다. [계약 상세](../handbook-durable-projection-contract.md).

Codex 작업자는 구현(Sol/high)과 별도 프로세스 검증(Astra/high)을 나눠 맡고, 메인에서 공개·clean·
진단·배포 구성을 통합했습니다. 독립 검증 35개가 실제 추출 함수 호출을 계측했습니다. 원본 7개인
테스트 프로젝트에서 첫 빌드 7회, 새 프로세스 재실행 0회, 의존 원본 변경 후 3회였으며 결과 본문·
전체 근거·생성 식별자가 전체 재계산과 같았습니다. 측정은 각각 503/427/491ms, clean 미리보기
161ms였으나 인터프리터 시작을 제외하고 명령 경로도 다르므로 **실사용 속도/지식 품질의 개선 증거가
아닙니다.** 저장 작업자는 49개, 프로세스 메모 테스트는 18개를 통과했습니다.

구현/배포 파일을 고정한 최종 메인 회귀 검증에서 **Python 641개 / 612.306초**가 모두 통과했습니다.
독립 실행 간 통합/저장 검증, MCP·갱신·공개·설치기와 기존 호환성 테스트를 포함합니다. 셸 문법과
diff 공백 검사도 통과했습니다. 테스트 본체와 확인한 장기 실행 테스트 자식이 종료됐으며 실제 엔진은
복구 당시 PID, health 200, MCP 조회 성공을 유지했습니다. 테스트 로그의 가짜 빈 메모리 공간을
실제 프로젝트 그래프 상태로 해석하지 않습니다.

메인에서 실제 작업 저장소를 읽기 전용으로 확인했을 때 원본 116개와 인용 21개를 선택했습니다.
일반 cold 미리보기(581.3ms)와 clean 미리보기(677.5ms)는 각각 116회 추출했으며 본문·근거·생성
식별자가 같았습니다. 캐시를 생성/변경하거나 안내서를 공개하지 않았습니다. 이는 실제 저장소의
결정론적 결과 확인이며 실행 간 warm 성능 측정은 아닙니다. 그 검증은 격리된 테스트에 한정합니다.

사용자가 기존 ByoriDB 서비스만 다시 시작하도록 명시적으로 승인했습니다. 설치된 v0.4.13의
manifest/서명을 검증한 뒤 기존 plist를 기동하여 health 200과 이 대화의 실제 MCP 기억 조회를
복구했습니다. 업데이트·재설치·인증/호스트 설정 변경·데이터 삭제는 하지 않았습니다. 수정한 네이티브
테스트 **353개 / 16.729초**와 자체 검증이 통과한 뒤에도 같은 엔진 PID와 정상 응답을 확인했습니다.
8–11절의 메모리 미연결은 당시 기록이며 현재 상태가 아닙니다. 원래 종료에 대한 이전 자체 검증의
영향 가능성과 단정할 수 없는 범위는 그대로 남깁니다.

ByoriDB 메모리 스킬로 확정 전략을 조회하고, 장애·테스트 격리 수정과 관계 및 중간 결과 모듈의
계약 위치를 기록했습니다. 다시 조회하여 장애와 원인 관계가 저장된 것을 확인했습니다. 제품 문서가
단계별 검증 기록이며, 이 저장 성공을 그래프 원본의 자동 이전 성공으로 표현하지 않습니다.

KC-03 전체나 제품 목표의 완료는 아닙니다. 실제 호스트 수신, 안전한 오프라인 이전 결과 전달,
그래프 원본 보존/이전, 데이터/런타임 전체 복구, 화면·아키텍처·서명 검증과 비교 실사용 평가가 남아
있습니다. 커밋·푸시·릴리즈·실제 호스트 모델 호출·실제 프로젝트 안내서 공개를 수행했다는 의미가 아닙니다.
